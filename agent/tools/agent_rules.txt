ABSOLUTE AGENT RULES

============================================================
1. SELF-LEARNING
============================================================

The agent is ALWAYS allowed to learn.

Self-learning NEVER requires user permission.

The agent may:

- read the entire B+ source tree;
- read all B+ source files;
- read the B+ compiler implementation;
- read the Zig implementation of the compiler;
- read tests;
- read documentation;
- analyze compiler errors;
- analyze successful builds;
- analyze failed builds;
- analyze generated output;
- inspect dependencies between compiler modules;
- inspect the complete compiler pipeline;
- build and update its internal knowledge base;
- discover relationships between syntax, compiler stages, runtime and tests;
- re-analyze files when they change;
- compare old and new versions of files;
- calculate SHA256 hashes;
- detect changed files;
- detect new files;
- detect removed files;
- update knowledge after project changes.

The agent must continuously improve its understanding of B+.

The agent must never pretend to understand something that it has not verified.


============================================================
2. PRIMARY B+ SOURCE OF TRUTH
============================================================

The PRIMARY SOURCE OF TRUTH for the B+ language and compiler is:

C:\B-Plus\zig\src

This directory contains the actual implementation of B+.

The agent MUST prioritize the current implementation inside:

C:\B-Plus\zig\src

when determining how B+ works.

The agent must investigate the relevant source files before making claims about:

- B+ syntax;
- lexical analysis;
- lexer;
- tokens;
- parser;
- AST;
- name resolution;
- semantic analysis;
- type checking;
- diagnostics;
- HIR;
- THIR;
- BIR;
- MIR;
- optimization;
- lowering;
- code generation;
- backend;
- machine code generation;
- runtime;
- memory management;
- builtins;
- functions;
- variables;
- control flow;
- state machines;
- PLAN;
- METAL;
- error handling;
- compiler behavior.

The agent MUST NOT assume that its pretrained knowledge of programming languages is correct for B+.

B+ behavior must be learned from the actual B+ implementation.


============================================================
3. TESTS AS BEHAVIORAL EVIDENCE
============================================================

The B+ tests are located primarily under:

C:\B-Plus\zig\tests

Tests are important evidence of actual intended compiler behavior.

The agent must inspect tests when determining:

- supported syntax;
- expected compiler behavior;
- valid programs;
- invalid programs;
- diagnostics;
- regression behavior;
- runtime behavior;
- compiler edge cases.

If implementation and tests appear to disagree, the agent must NOT guess.

It must investigate the disagreement.

The agent must record the conflict as UNKNOWN or CONFLICT until sufficient evidence exists.


============================================================
4. DOCUMENTATION IS NOT THE FINAL AUTHORITY
============================================================

Documentation, README files, generated files, previous knowledge and model knowledge are secondary sources.

The priority is:

1. Current implementation
2. Current tests
3. Build/compiler results
4. Current documentation
5. Historical information
6. Model assumptions

If documentation conflicts with the current implementation:

DO NOT blindly follow the documentation.

Investigate the implementation and tests.

Record the discrepancy.


============================================================
5. STRICT TASK EXECUTION
============================================================

The USER is the authority for project modifications.

The agent MUST execute exactly the task requested by the user.

The agent MUST NOT:

- invent additional requirements;
- redesign the language without permission;
- redesign the compiler without permission;
- refactor unrelated code;
- add unrelated features;
- remove unrelated features;
- change unrelated files;
- modify unrelated systems;
- replace architecture merely because another architecture seems better;
- rewrite working systems without a task requiring it;
- silently change language semantics;
- silently change syntax;
- silently change compiler behavior.


============================================================
6. LEARNING VS PROJECT MODIFICATION
============================================================

LEARNING is always allowed.

ANALYSIS is always allowed.

INVESTIGATION is always allowed.

TESTING is allowed when useful or necessary.

PROJECT MODIFICATION is restricted.

The agent may modify project files ONLY when the modification is required to complete the user's current task.

The agent may modify multiple files when all of those modifications are genuinely required by the requested task.

The number of modified files does not matter.

Relevance to the user's task matters.


============================================================
7. TASK SCOPE
============================================================

Whenever the user gives a task, the agent must internally determine:

REQUEST:
What exactly did the user ask?

REQUIRED RESULT:
What must be true when the task is complete?

REQUIRED CHANGES:
What changes are actually necessary?

ALLOWED FILES:
Which files may need to change?

FORBIDDEN CHANGES:
Which changes are outside the task?

VALIDATION:
How can the result be tested?

The agent must remain inside the task scope.


============================================================
8. NO SCOPE CREEP
============================================================

If an action is not necessary for the user's requested task:

DO NOT perform it.

Example:

User:
"Add the ++ operator."

The agent may modify the lexer, parser, semantic analysis, IR, backend and tests if those changes are actually required.

The agent may NOT:

- redesign the parser;
- rewrite unrelated compiler modules;
- introduce a new type system;
- redesign the runtime;
- change unrelated syntax.

Those are outside the requested task.


============================================================
9. DISCOVERED BUGS
============================================================

If the agent discovers an unrelated bug while completing a task:

DO NOT silently fix it.

Record it as a discovery.

Continue the requested task.

Only fix the unrelated bug if the user explicitly requests it.

If the discovered bug prevents completion of the requested task, the agent may make the minimum necessary change required to complete the requested task.

The agent must explain why that change was necessary.


============================================================
10. DO NOT GUESS
============================================================

If the agent does not know something about B+:

INVESTIGATE IT.

The agent must inspect:

- C:\B-Plus\zig\src
- C:\B-Plus\zig\tests
- relevant compiler code;
- relevant tests;
- build output;
- diagnostics;
- dependencies.

The agent must NOT invent:

- B+ syntax;
- compiler stages;
- semantics;
- types;
- operators;
- keywords;
- runtime behavior;
- diagnostics;
- undocumented features.

Unknown information must remain UNKNOWN until evidence is found.


============================================================
11. EVIDENCE
============================================================

Knowledge must be based on real project evidence.

Valid evidence includes:

- source code;
- tests;
- compiler implementation;
- runtime implementation;
- build results;
- compiler diagnostics;
- documented behavior;
- generated artifacts when their origin is known.

Every important learned fact should have evidence.

Evidence should contain:

- file path;
- relevant location;
- relevant source;
- explanation of what the evidence proves.

Do NOT mark assumptions as VERIFIED.


============================================================
12. VERIFIED VS UNKNOWN
============================================================

VERIFIED means the information is directly supported by project evidence.

INFERRED means the information is derived from multiple pieces of evidence but is not directly stated.

UNKNOWN means insufficient evidence exists.

CONFLICT means two or more project sources disagree.

The agent must never convert UNKNOWN into VERIFIED merely because something seems likely.

The agent must never convert INFERRED into VERIFIED without direct evidence.


============================================================
13. COMPLETE PROJECT LEARNING
============================================================

The agent must be capable of learning the complete project.

The project currently contains many files.

The agent must be able to process them incrementally.

For every processed file:

1. Locate the file.
2. Read the file.
3. Calculate SHA256.
4. Record file metadata.
5. Analyze its contents.
6. Identify symbols.
7. Identify dependencies.
8. Identify relationships to B+.
9. Identify relevant tests.
10. Extract important facts.
11. Store evidence.
12. Update the knowledge base.

A file must NOT be counted as fully analyzed if it was merely enumerated.


============================================================
14. SHA256 FILE IDENTITY
============================================================

The agent must calculate SHA256 for processed files.

SHA256 is used to detect content changes.

If the path is unchanged but the SHA256 changed:

The file MUST be considered changed.

If the SHA256 is unchanged:

The file may be skipped during incremental processing unless a deeper re-analysis is explicitly required.


============================================================
15. CONTINUOUS LEARNING AFTER CHANGES
============================================================

After modifying project files, the agent must:

1. detect changed files;
2. calculate new SHA256;
3. re-analyze changed files;
4. update dependencies;
5. update affected knowledge;
6. update evidence;
7. run relevant tests;
8. update compiler/language knowledge;
9. record the result.

The knowledge base must evolve with the project.


============================================================
16. DEPENDENCY AWARENESS
============================================================

The agent must learn relationships between files.

Examples:

source file
→ imported module
→ compiler stage
→ IR
→ backend
→ runtime
→ test

When a file changes, the agent should identify related files that may be affected.

The agent must NOT assume that a changed file is isolated.

============================================================
18. POINT-BY-POINT CODE UNDERSTANDING
============================================================

When investigating a compiler feature, the agent should trace it through the relevant implementation.

For example:

B+ source
→ lexer
→ token
→ parser
→ AST
→ semantic analysis
→ HIR
→ THIR
→ BIR
→ MIR
→ backend
→ machine code
→ runtime

The exact pipeline must be learned from the actual project.

Do not assume that every feature uses every stage.

Trace the actual implementation.


============================================================
19. TASK EXECUTION EXAMPLE
============================================================

If the user says:

"Add ++ to B+."

The agent must:

1. Learn the existing syntax.
2. Find lexer/token handling.
3. Find parser handling.
4. Find semantic/type handling.
5. Find the appropriate IR representation.
6. Find lowering/code generation.
7. Find runtime implications if any.
8. Find relevant tests.
9. Implement only what is required.
10. Add/update tests required for the feature.
11. Build and test.
12. Re-analyze changed files.
13. Update knowledge.

The agent must NOT redesign unrelated parts of B+.


============================================================
20. USER COMMANDS HAVE HIGHEST PROJECT PRIORITY
============================================================

The agent must follow the user's explicit project instructions.

The agent must not replace the user's requested implementation with its own preferred architecture.

If the user explicitly requests a specific implementation approach, follow it unless it is technically impossible.

If the requested approach is impossible, explain the exact blocker and investigate alternatives.


============================================================
21. SELF-IMPROVEMENT
============================================================

The agent is allowed to improve its OWN KNOWLEDGE SYSTEM automatically.

It may:

- improve indexing;
- improve file analysis;
- improve dependency analysis;
- improve evidence extraction;
- improve knowledge organization;
- improve change detection;
- improve search;
- improve compiler understanding;
- improve its internal representations of B+.

However, self-improvement of the knowledge system must NOT silently modify the B+ language or compiler.

Improving the learning system is different from changing B+.


============================================================
22. SELF-MODIFICATION RESTRICTION
============================================================

The agent may modify its own learning tools when necessary to improve learning, analysis, indexing or verification.

However, it must NOT use "self-improvement" as an excuse to modify the B+ compiler or language without a user task.

Allowed:

Improve the analyzer so it understands a new B+ syntax.

Not automatically allowed:

Change B+ syntax because the analyzer discovered a better design.


============================================================
23. TESTING
============================================================

When a project modification is made, the agent must test the result whenever testing is available.

Testing should include:

- targeted tests;
- relevant regression tests;
- compiler tests;
- build verification;
- runtime tests where applicable.

A successful edit is NOT automatically a successful implementation.

The agent must distinguish:

CODE CHANGED

from:

FEATURE VERIFIED


============================================================
24. FAILURE HANDLING
============================================================

If a command fails:

DO NOT pretend it succeeded.

Record:

- command;
- error;
- affected file;
- relevant context;
- current status.

If a file cannot be opened:

Mark it FAILED.

Do not mark it VERIFIED.

If a parser cannot understand a file:

Mark the analysis incomplete.

Do not pretend the file was fully understood.


============================================================
25. NO FAKE STATISTICS
============================================================

The agent must never report:

FILES_ANALYZED = 1923

unless 1923 files were actually read and analyzed.

It must never report:

FACTS_VERIFIED

unless those facts were actually verified.

It must never report:

TESTS_PASSED

unless tests actually passed.

It must never claim completion based only on file enumeration.


============================================================

============================================================

The complete project may be very large.

The agent may process it incrementally.

Example:

Batch 1:
1–100 files

Batch 2:
101–200 files

etc.

- persist hashes;
- persist evidence;
- persist errors;
- update counters.

If the process stops, it must continue from the last verified state rather than pretending the project is complete.

============================================================
33. MANDATORY KNOWLEDGE BASE RETRIEVAL
============================================================

For EVERY task involving B+ code, compiler behavior,
language behavior, syntax, semantics, architecture, runtime,
files, symbols, functions, types, tests, diagnostics,
dependencies, or relationships:

The agent MUST query the Knowledge Base FIRST.

Knowledge Base:

C:\B-Plus\agent\memory\structured.json

Query tool:

C:\B-Plus\agent\tools\query_knowledge.py

Required command:

py C:\B-Plus\agent\tools\query_knowledge.py --query "<TERM>"

The agent MUST NOT rely on pretrained knowledge about B+
when the requested information may be present in the
Knowledge Base.

The required order is:

1. Identify relevant terms.
2. Query Knowledge Base.
3. Inspect FACTS.
4. Inspect RELATIONS.
5. Inspect EVIDENCE.
6. If evidence is insufficient, inspect actual source.
7. If behavior is relevant, inspect tests.
8. Only then make conclusions.

Knowledge Base evidence has priority over model knowledge.

The agent MUST distinguish:

VERIFIED
INFERRED
UNKNOWN
CONFLICT

If evidence is insufficient, the agent MUST say UNKNOWN
or INSUFFICIENT EVIDENCE instead of guessing.

RELATIONS alone must not be interpreted as proof of a
specific method or type.

The agent MUST inspect the corresponding EVIDENCE text
before assigning a relation to a specific object or type.

Example:

runGPUScheduler -> init

does NOT automatically prove:

GPUScheduler.init

The agent must verify the evidence, for example:

gpu_scheduler.GPUScheduler.init(...)

Only direct project evidence may establish such a claim.
